# 创新点 · dsh-lumen

这份文档记录 `dsh-lumen` 在哪些地方做了和常见壁纸 / 换肤插件不同的技术选择，以及**为什么**这么选。每一条都对应代码里的具体位置和一组会失败的测试——不是营销话术，是可验证的设计决定。

---

## 出发点：换一个待解决的问题

绝大多数壁纸插件的核心问题是 **"现在显示哪张图"**。

`dsh-lumen` 认为这个问题只解决了一半，于是把问题换成两个：

1. 现在显示什么？
2. **下一次什么时候变，变成什么？**

第二个问题才是这个插件存在的理由。它把一个"贴图工具"变成了一个**调度器**——而调度器要处理的东西（时间、顺序、错过、暂停）和贴图工具完全不同。

下面按"这个决定带来多少结构"排序。

---

## 一、轮播调度器（主要创新）

### 1.1 四种触发方式，对应四种真正不同的"时间"

很多插件说"定时换壁纸"，实际只实现了"每 N 分钟"。但用户说的"定时"至少对应四种不同的心智模型，把它们混成一种会同时让四种人都不满意：

| 模式 | 语义 | 谁需要它 |
| --- | --- | --- |
| `interval` | 每 N 分钟（5–43200） | "别老是同一张" |
| `hourly` | 每小时的第 N 分钟（可多选） | 希望换图落在可预判、可安排的钟点上 |
| `daily` | 每天某个本地墙钟时刻 | "每天早上换一张" |
| `session` | 每次重新看向应用时 | **与钟表无关** |

最后一种值得单独说：`session` 模式**由可见性驱动，不由时间驱动**。对"每次会话"来说钟表本来就是无关变量，所以它不看 `Date.now()`，也就天然不受睡眠、时钟跳变、夏令时影响。把它硬塞进"每隔 N 分钟"的框架里，就得去猜一个用户根本没指定的 N。

### 1.2 网格锚定，而不是"距上次 N 分钟"

`interval` 模式听起来最直白的实现是：换完图 → 起一个 N 分钟的计时器 → 到点换 → 重起计时器。

这个实现有个隐蔽的缺陷：**每次页面刷新都会重置计时器**。一个习惯频繁刷新的用户会永远等不到第一次更换；而且每次重启都从零开始，时间点会离钟面越来越远，用户无法预期。

`dsh-lumen` 的做法是**锚定网格**：以启用轮播的那一刻为锚（`anchorAt`），之后严格踩在锚点上。同一份 `(schedule, now)` 输入永远给出同一个下一次触发时刻，与"已经过了几次""刷新过几回"无关。

这个决定让调度器变成**无状态**的——它不需要记住"上次是什么时候换的"。状态里只留一个 `nextAt`，而它也只是个缓存，随时可以由纯函数重算。

### 1.3 洗牌不等于"每次随机抽一张"

"随机"有两种常见实现，其中一种是错的：

- ❌ 每步从列表里独立随机抽一张 —— 会出现连续两次抽到同一张，用户会觉得"没换"
- ✅ 洗出一轮队列，**走完一轮之前不重复** —— Fisher–Yates 洗牌，逐个出队

`dsh-lumen` 两种都提供，但分成了两个明确的模式：`shuffle`（洗牌队列）和 `random`（每步独立随机），并在界面上分别说明差异。默认推荐洗牌。

洗牌队列带来一个真实的边界情况：**队列是用旧列表长度算的**。用户要是中途加了一张图或删了一张，队列里的下标就可能指向不存在的项。所以顺序一变，`orderRevision` 自增，旧队列作废重洗。这个字段单独存在，就是为了让这件事显式而可测。

### 1.4 有损追赶：睡过五次，只换一次

笔记本合盖睡了八小时，醒来时已经错过五个触发点。应该怎么办？

- **补播**：在用户眼前闪五张图，烧 CPU 去追一个只有最后一次才有意义的中间状态
- **有损追赶**：直接跳到最新状态，只换一次

`dsh-lumen` 选后者，并把取舍集中在一个函数 `planResume` 里，而不是散落在定时器回调的条件判断中。这样"睡过 N 个触发点只前进 1 步"是一条能被断言的规则，而不是一个偶然的行为。

### 1.5 纯函数 + 一个定时器

整个调度模块是 `(schedule, now) -> number` 的纯函数集合。浏览器半边只负责持有**一个**定时器，以及一次唤醒检查。

为什么这件事重要：调度器的难点**全部**在边界情况——睡过三个触发点、设备时钟被往回拨、夏令时跳变、洗牌模式下只有两张图的列表、播放列表被清空。

而这些情况**没有一个能通过 `setInterval` 诚实地测出来**。用真定时器测这些，测试要么跑得极慢，要么依赖 sleep 和时序巧合，要么直接跳过最难的部分。

写成纯函数之后，它们就是普通的单元测试：

> 把"现在"设成 `T`，断言返回值等于 `T'`。

`tests/scheduler.test.cjs` 就是这么做的——包括把时钟往回拨之后的行为，以及"7 天跳变只前进一步"。

## 二、可读性下限：求解而不是要求

### 2.1 为什么壁纸插件必须同时是洗色插件

引擎的根节点是 `position: fixed; inset: 0; z-index: -1`，在应用后面，且不收指针事件——所以它对宿主的布局、命中测试、滚动没有任何影响。

但**正因为它在后面**，要让它可见，应用的画布必须是半透明的。所以壁纸插件不可避免地也是一个洗色（wash）插件：它把主题自己的画布色换成**同一个颜色的半透明版本**。

### 2.2 只碰两个 token

洗色**只**覆盖两个 token：

```
--dsw-alias-bg-base            画布
--dsw-specific-sidebar-fill    侧栏面板
```

刻意不碰其他。对比一下：皮肤类插件往往还要覆盖输入框和对话框的填充色，因为它的目标是控制材质系统。**壁纸插件没有理由改写输入框的材质。** token 面越小，未来宿主换代时被牵动的面积就越小。

### 2.3 用户不小心关不掉的对比度保护

壁纸可以以任何主题 token 都拦不住的方式毁掉文字对比度：画布被洗成半透明，压在一张任意图片上。

所以洗色 alpha 对着 **WCAG 2.1 AA（4.5:1）** 求解，实际生效值取 **"用户设定"与"求解下限"中较大者**。

这里最容易做错、也最值得说的是**在哪个色彩空间里算**：

- 对比度公式里的*相对亮度*是**线性光域**的量；
- CSS `rgba()` 的 alpha 混合发生在**伽马编码域**。

混用这两者会在中间调上偏掉一大截——一个看起来"算对了"的实现，实际渲染出来的对比度可能差 20% 以上。

`color.cjs` 的处理是：把壁纸归约成一个**相对亮度相同的中性灰**（亮度估计本身就是线性域的加权平均，所以它在通道空间的等效平坦色恰好是它的平方根），在通道空间里做合成，再对 alpha 二分。12 次迭代收敛到 0.1%，且结果**向上取整**——它是安全下限，向下舍入会交出一个达不到目标的 alpha。

### 2.4 面板显示差异，而不是隐藏它

一个滑块显示 30%、实际渲染 62% 而且不吭声，是这个项目刻意避免的谎。

抬升发生时，面板会把**实际生效值**和**抬升原因**显示出来（`appearance.raised`）。用户看到的是"你设了 30%，但为了保证文字可读我用 62%"，而不是一个对自己不诚实的数字。

### 2.5 "画面有多花"按覆盖面积估，而且故意高估

自动弱化需要知道一张图有多"花"。`estimateImageLuminance` 的做法是**自下而上按覆盖面积加权合成**，而不是数色标个数。

区别很实际：一层覆盖 80% 画面的亮色，比八层各覆盖 5% 的亮色危险得多。数色标个数会把后者的分数算得远高于前者——正好算反。

另外估计**故意偏向高估亮度**。因为估计偏高的代价是"洗色稍微厚一点"，估计偏低的代价是"用户看不清字"。不对称的代价要按不对称的方式处理。

### 2.6 能测就测，别估：把常数换成实测值

上面那套估计有一个前提：**拿得到画面的描述**。配方和渐变都是插件自己算出来的，所以这个前提成立。

**图片地址不成立**，而且是双重的不成立：渲染路径是同步的，没有像素可看；就算异步补上，跨域图片画进 canvas 会污染画布，`getImageData` 直接抛错。所以远程图片只能沿用那个中性常数——这是它唯一诚实的答案。

**本地图片不成立的理由不成立。** `prepareImage` 在导入那一刻手里已经握着解码后的位图。把它画进一张 64×64 的小画布读一遍像素，只多一次绘制，而收益是把一个常数换成这张照片**真实的**亮度。之所以这是"免费的"，是因为测量点选在了**解码循环之前**：那里位图一定在，而且亮度本来就是"用户挑的那张图"的属性，不是"我们恰好施加的那次缩放"的属性。

**读数取上四分位，不取平均值。** 平均值回答的是"这张图平均多亮"，这是错的问题。文字压在画面的**某一块**上，要紧的是"亮到足以威胁对比度的那部分有多亮"：

| 画面 | 平均值 | 上四分位 |
| --- | --- | --- |
| 半黑半白 | 0.5 | **1.0** |
| 纯中灰 128 | 0.216 | 0.216 |

半黑半白的图按平均值 0.5 求解洗色，白的那一半照样读不了；上四分位给的是 1.0。而在平坦画面上分位会塌回平均值附近，所以**不存在"白白多洗一层"的代价**——保护只在真有亮区时才发生。用 nearest-rank 而不是插值，还保证了返回值永远是**某个像素真正有过的亮度**，而不是两个采样点的平均值（那个值不落在任何像素上）。

**"没有测量"和"纯黑"必须是两个不同的值。** 读不出来时返回 `null`，不返回 `0`：

- `null` → 引擎回退到中性常数；
- `0` → 纯黑，恰恰是唯一会让可读性下限彻底失效的输入。

这个区别在代码里只差一个字符，所以它在**两个方向上都设了防线**：`normalizeLuminance` 严格按类型判定（`Number(null)` 是 `0`，宽松转换会把"未测量"静默变成"纯黑"），`sampleLuminance` 在任何失败路径上都返回 `null` 而不是猜。测试对这两条都单独断言了。

顺带一提，这个值**不占新的存储键**：它嵌在条目所在的 JSON 字段里，只有图片字节本身才各自占一个 blob 键。所以加实测亮度不会挤压 `MAX_STATE_KEYS`，也不需要抬 `schema` 版本——旧文档读到新版本渲染结果逐像素相同，新文档被旧版本读到只是退回常数。

## 三、零素材的程序化壁纸

内置的生成式壁纸**不打包任何图片**。它们是参数化配方，运行时用 CSS 渐变算出来。另外四张随包插画是作者为这个包画的，走的是同一套渲染与洗色链路，只是 `build()` 里返回一层 `url()`。

这样做换来三件事：

1. **体积不随可选壁纸数量增长。** 加到 50 套也不会多一个字节的素材。
2. **零版权风险。** 没有素材就没有授权问题——这在一张壁纸可能价值数千元的授权市场里不是小事。
3. **可派生。** 每个配方都接受一个 `seed`，同一配方换种子就是同风格的另一种构图。所以一个配方其实是一整个连续空间，而用户可以复制种子分享给别人、精确复现同一张图。

配方的选择也遵守一条纪律：只有**浅浅几层**大范围渐变 + 少量点状高光。壁纸在应用后面，任何"有存在感"的细节都会在长时间使用中变成干扰。

## 四、跨 origin 的两层持久化

### 4.1 问题

DSH Desktop 每次启动都把 Web 服务绑到**系统随机分配的端口**，因此页面 origin 每次都变。而 `localStorage` 是按 origin 隔离的。

结果：纯前端插件会在每次重开应用时"忘记"用户的壁纸。数据其实还在浏览器的 leveldb 里，只是被记在旧端口名下。这不是插件的 bug，是架构的必然后果——**但用户感知到的是"这个插件记不住我的设置"**。

### 4.2 两层，各司其职

- **权威副本**在宿主侧：`$DSH_HOME/lumen.json`，经受围栏保护的 `/lumen/api` 路由读写，原子写（临时文件 + rename）。
- **`localStorage` 只当种子**：它是**同步**的，所以刷新后第一帧画出来就已经是正确的壁纸，而不是先闪一下默认值再等 HTTP 往返。宿主答复返回后替换掉它。

两层共用**同一份扁平序列化格式**（`dsh-lumen:` 前缀键）。这件事很关键：如果种子有自己的格式，那么往其中一层加字段时，另一层会静默缺失，而错配只在"首帧画错"这种最难复现的现象里暴露。

### 4.3 写入携带意图，而非整份文档

宿主 API 是**合并**语义：缺席的键保持原值，显式 `null` 删除。

所以插件只推送用户（或轮播引擎）真正改动的字段，并为消失的负载键推 `null`——一个曾被写入、现在已不存在的键**必须**删除，否则移除一条播放列表项会把它的图片字节永远留在磁盘上。

推整份文档会简单得多，而且是错的：两个 DSH 窗口共享同一个 `$DSH_HOME/lumen.json`，只改了壁纸的那个窗口会把另一个窗口的洗色、微调和调度一起回滚掉。

### 4.4 存储分层：一张图顶爆配额，不该带走其他设置

偏好在一个小 JSON 文档里，图片各自占一个键（宿主文件里是 `blob:<id>`，浏览器种子里是 `dsh-lumen:blob:<id>`）。

这样一张塞不进去的图**只让它自己失败**——播放列表、调度和洗色都不受影响。

反例是把包括数兆字节 data URL 在内的所有偏好塞进同一张扁平表。那样也能用，但让**整份文档**暴露在单个超大值的风险下：一张 6MB 的照片足以把存储配额顶爆，顺手带走用户的全部设置。

### 4.5 状态文件刻意保持"扁平 + 字符串"

`$DSH_HOME/lumen.json` 是一个扁平 map，值一律是字符串。

这是为了跨版本共存：文件被所有解析到同一 `DSH_HOME` 的进程共享——Web profile 和桌面外壳可能同时在跑，甚至跑着**不同版本的插件**。

如果它是嵌套结构，一个旧版构建会把新版的嵌套对象读成 `"[object Object]"`，然后**把它当成一个偏好写回去**。扁平字符串 map 则退化成"一个我们不认识的键，忽略掉"。

图片负载因此是独立的键，而不是某个嵌套字段——这不是设计偏好，是兼容性要求。

### 4.6 开屏的字节不落在状态文件里

同一条分层规则，在开屏上比在壁纸上更硬性：壁纸是几百字节的渐变字符串，20 秒视频是 **2 MB**——差了三到四个数量级。

状态文件是**扁平字符串 map，上限 24 MiB**，而且被所有解析到同一 `DSH_HOME` 的进程共享。把媒体字节塞进去会同时踩两条线：单次请求体上限，和整份文档的上限。

所以媒体走第三条路：**字节留在磁盘**（`$DSH_HOME/lumen-media/`），状态里只留**文件名**。

这里有个比"省空间"更重要的收益：**服务哪个文件，是由一段白名单形状拼出来的，而不是由请求里的字符串拼出来的**。名字由宿主生成（`media-<时间戳36>-<8位hex>.<扩展名>`），扩展名只从请求的 `content-type` 经一张允许表反查，读取时再按同一个形状校验一遍——**没有任何一条代码路径会 join 请求里的内容**。路径穿越在这种设计下不是"被防住了"，而是"不存在"。

替换与清除的删除顺序也是刻意选的：**先改状态，再删文件**。反过来一旦状态写入失败，就会留下一个指向已消失文件的偏好——用户看到的是一块坏掉的开屏；而按这个顺序失败，留下的只是一个没人引用的文件，是惰性的。

## 五、预览即真身，而且可以拨钟

### 5.1 预览跑的是要发布的那个包

预览页加载真实的 `lib/client.js`，通过一个替身提供 `window.__ModuleLoader__`、`react` 种子，以及带 `theme` / `slots` / `locale` 的 ctx。

所以右侧显示的设置面板**就是面板本身**，不是效果图；壁纸渲染走的也是同一份引擎代码。一个"预览很好看、装上去不是那样"的插件，本质上是预览在骗人。

**宿主半边也一样，而且是字面意义上的"挂上去"。** 预览服务器 `import()` `lib/index.js` 然后调它的 `apply()`，拿到的是**它自己注册的路由**、它自己的状态文件、它自己的围栏、它自己的状态合并。服务器不实现任何一条协议。

这条曾经不是这样：早先的 `serve.cjs` 把状态读写、合并、路由复刻了一遍。那是个更难发现的错误——**它不会报错**。两个实现会在"改了一边忘了另一边"时安静地分叉，而"预览能跑通"就再也不能推出"宿主能跑通"。真正的代价不是重复的代码量，是**预览的证明力**：一个复刻件能证明的最多是"复刻件是自洽的"。

代价是加载顺序变成了契约：宿主半边把媒体目录钉在 `$DSH_HOME` 上，而 `$DSH_HOME` 必须在**模块加载之前**设好，所以服务器要先定 `DSH_HOME`、再 `import()`。这一条写在了 `serve.cjs` 里，因为顺序错了不会报错，只会安静地写到错误的目录。

### 5.2 所有读数都是算出来的

预览里「覆盖了 2 个 token」这一行，是把引擎的 `rawTokens()` 和 `visibleTokens()` 做**差**得到的，不是复述一个常量。

如果哪天覆盖面变成 3 个 token，这一行会跟着变成 3，并标黄。**读数是唯一不会替代码说好话的东西**，所以它应该从代码里长出来，而不是从文档里抄。

### 5.3 开屏要单独一个页面，因为它是文档级的

预览的主页面（`preview/index.html`）**不带** `data-dsh-lumen-shell-document`，所以注入器永远不往它里面放遮罩——否则每刷一次预览都要等一次开屏，工具就变成障碍了。

开屏走 `preview/boot.html`：它是外壳 `index.html` 的替身，带那个标记，因此会真的被注入那两行。它的 `#root` 里有一个 `[data-dsh-boot]`，`boot.js` 用**两帧**把它换掉。

两帧不是一帧，这条值得记：`requestAnimationFrame` 的回调跑在它所属那次**绘之前**，所以"在第一帧回调里换掉"等于内核从来没上过屏。而真实交接（`BootHandoff`）是会让内核上屏一次的——开屏的释放时机正是卡在"标记在、然后没了"上，替身必须复刻**两个时刻**，不是一个。

外壳这半边的事实不是猜的：`mountApp` 用 `container.querySelector(":scope > [data-dsh-boot]")` 找内核，`BootHandoff` 渲染它一个 commit 然后换成 `app()`，`<div id="root"></div>` 是空的——这些是从 `app.asar` 里读出来的。**先读契约再照着写**，和"照着观察到的现象写"，差别就在这里：后者会在某个版本换了实现之后安静地失效。

### 5.3 拨钟：调度器最难测的是时间

预览里有一排 `+15 分 / +1 小时 / +1 天 / +7 天` 按钮，会**真的平移 `Date.now()`**，然后走一遍和真实时钟跳变完全相同的代码路径（触发补上错过的轮次）。

关于拨钟有一个容易做错的地方，值得单独记下来：

> **一个恒定偏移只是同一条时间轴的重新标注，所以只有"现在"的来源需要移动。**

`new Date(ts)`、`new Date(y, m, d, ...)` 以及所有 getter 都**必须原样不动**。否则 `nextTriggerAt - Date.now()` 会因为偏移量而整体错位——时间源和计算出来的触发时刻不在同一个参照系里。

预览的时钟垫片因此只改两处：`Date.now()` 和无参 `new Date()`。

测试断言的是**后果**而不是实现方式：平移之后，算出的延迟仍然落在一个周期之内。断言后果而非机制，是因为机制可以换（比如将来垫片换成别的写法），而后果是这个功能对用户的承诺。

## 六、把"失败"也设计进去

### 6.1 插件入口从不抛异常

cordis 的 loader entry factory 一旦抛出，会聚合到宿主层的 "entries did not activate"，**连带整个 Web 外壳一起挂掉**。

用户的整个应用因为一个壁纸插件出问题而起不来——这个代价和收益完全不成比例。

所以 `src/index.cjs` 里每个平台服务都先用 `typeof` 探一遍，每次注册都包在 try 里，失败模式永远是"壁纸不出现 + 控制台一行日志"，而**不是**"DSH 起不来"。它导出的 `inject` 列表里缺任何一个服务都只是降级，不是崩溃。

### 6.2 归一化做一次，而且是钳制而非仅类型检查

所有到达状态模型的东西都经过文本通道：磁盘上的 JSON、`localStorage`、或者被手工编辑过的值。任何一个都可能是**过期的**（由未来版本写入）、**截断的**、或者**有敌意的**（同源页面脚本写进同一份存储）。

下游消费者（CSS 字符串构造器、定时器、token 覆盖）都假定输入已经是正确形状，所以归一化**只做一次**，在 `state.cjs` 里，而且每个字段是**被钳进值域**而不是仅做类型检查：

> 读到一个透明度 `3.4`，这不是一个需要上报的错误，它是一个应当渲染为 `1.0` 的值。

### 6.3 设置面板原地同步，不重建 DOM

面板构建一次，之后 `sync()` 把当前状态推进每个控件。

每次改动都重建 DOM 写起来更简单，但会在拖动中途把指针底下的节点换掉——**每个滑块都会拖不动**。所以只重渲染真正呈列表形态的部分（配方卡片、播放列表、后续触发时刻），且仅在其内容变化时。

重绘通过 `requestAnimationFrame` 合并：拖动透明度滑块每个像素都会发一个 input 事件，不合并就是每帧重算一次配方和几千字符的 CSS 字符串。

### 6.4 围栏分三层，而且"抛异常就是拒绝"

插件自己有一条路由围栏：回环（或显式配置的可信 authority）的 `Host`，加同源浏览器标记。这条围栏一直是**忠实**的——它和宿主内部那份判断在双方都看得见的每一处都一致。

但它缺一层：**浏览器会话鉴权**。插件路由拿不到宿主的 `browserAuth`，唯一入口是宿主提供的 `connection.requestRejection`。只做自己那条围栏，即使判得再对，也**严格弱于宿主的自有路由**——因为宿主自己的路由会问两道，我们只问一道。

所以围栏改成三层，顺序固定，而且有两处刻意的不对称：

- **抛异常 = 拒绝，不是放行。** 检查者自己坏了就把门打开的围栏，不是围栏。工具函数里这是唯一正确的选择，因为它的失败模式是静默的。
- **只有 `undefined` 放行。** 宿主自己的 `admit()` 也是拿 `void 0` 比较而不是判 falsy；照抄这一点能让将来某个返回 `null` 的构建不至于在我们这边开门、在它那边关门。看不懂的返回值一律按拒绝处理。

还有两个不那么明显但同样重要的决定：

**服务是"探测"，不是"依赖"。** 把 `connection` 写进 `inject` 会让缺这个服务的构建**整个插件都挂不上**——那是把一次加固变成一次停服。所以它是探测出来的，读的时候用 `Reflect.get`，而且**每次请求都探测一次**：服务可能在插件挂载之后才被组装出来，一个在加载期就认定"不存在"的围栏会整整少一层，直到进程结束。

**缺层要出声，但只出一次。** 一条悄悄少了一层的围栏，比一条本来就没有那层的围栏更危险：从外面看两者一模一样，于是弱的那条会被当强的信。所以缺层时在**加载期**打一条告警——它是构建的属性，不是某一次请求的属性，按请求打就是噪音。

### 6.5 抢层叠序：唯一一个不需要猜的数字

视频开屏必须有一层压在一切之上。最容易的做法是随手写个很大的数——比如 `99999`——然后觉得"肯定够大了"。

但"够大"这件事是**没法验证的**。它依赖一个你无法穷举的前提：所有别的插件、以及将来可能装上的任何东西，用的数都比你小。而这个应用里浮层的既有惯例是"当前弹出的那个东西占最上层"，也就是说**别人会主动往很高的地方爬**——一个比上不足的常数被压住只是时间问题，而且只在别人恰好弹东西的那一瞬间被压住，属于最难复现的那类 bug。

所以这里取 **`2147483647`**，CSS 能接受的最大值。这个选择的好处是它**不需要任何外部知识**：一个别的元素依定义不得超过的值，就是唯一压不住的值。不需要读谁的分区注释，不需要知道现在装了哪几个插件，也不会因为别人升级就失效。

"不需要测量"这一点值得单独强调，因为它和直觉相反。直觉是"去把对手的层级读出来，然后取个更大的"。那个做法有个隐藏成本：读来的数字是**当下的**，一旦写进代码就成了一份会过期的快照——而快照的失效方式是安静的（别人升了级，你这边什么都不报）。最大值的论证没有快照。

所以测试里没有外部插件、没有绝对路径、没有"装了才跑、没装就跳过"的分支。它读 `engine.cjs` 里壁纸层真实的 `z-index`（而不是复述一个 `-1`），再断言层的值就是 **CSS 最大值**——**这个断言本身就是"压得住一切"的证明**，而不是它的代理指标。反过来，去量某个具体的对手层既更弱（量不到没想到的邻居）也更脆（那一个改了它就失效）。

顺带一个方法论：**断言越依赖外部世界，越容易退化成"看起来在检查、其实在跳过"。** 这条测试之前确实有过一个"邻居没装就 `t.diagnostic` 跳过"的分支——一条会静默跳过的交叉检查，比没有检查更坏，因为它占着"已验证"的位置却什么都没验证。去掉它之后，这条断言只依赖本仓库自己的两个文件，没有跳过路径。

层叠序本身也不是靠读数字定的，是问引擎问出来的：在真实 Chrome 里把四个同级层从负值一路铺到最大值附近，然后用 `elementsFromPoint` 看谁在上面。数字只在它自己的层叠上下文里有效，而"这个层到底在哪个上下文里"恰恰是读不出来的——`filter` / `transform` / `contain` / `will-change` / `isolation` 里任何一个出现在祖先链上，再大的 `z-index` 也只是在一个小盒子里当国王。实测结果与不变量见 [`SPLASH-SPEC.md`](SPLASH-SPEC.md) §八。

## 七、位置控制：把一条界面约束写进规格

这个控件存在的原因很具体：**DSH 左侧有一条常驻边栏**，居中构图的壁纸上，主体经常正好压在边栏底下。所以需要的不是两个连续滑块，而是九个格子——用户要回答的是"主体该往哪边挪"，这是个离散、粗糙、一眼就能选的问题。

九宫格比两条滑块好的地方有三处：它不需要标签（网格本身就是标签）；它一次就表达了九种选择；它的九种选择**恰好就是** CSS `background-position` 支持的九个关键字，中间不需要任何映射层。

### 7.1 一个刻意"明知无用"的写入

`position` 无条件写进两个图片槽，**不按 `fit` 分叉**。

在 `cover` / `blur` 下图片按视口比例铺满，`background-position` 不产生任何视觉变化——这段写入是"无用"的。之所以照写，是因为另一条路是"加一个只在 `contain` 下出现的分支"，而那样的分支需要自己的测试、自己的边界，并且在用户切换 `fit` 时行为会突然变化。**一条永远执行的路径比两条偶尔执行的好维护。**

只对 `bleed` 层例外：它恒定居中。它存在的目的是遮住上层 `contain` 的蒙版边，一旦偏心，恰好会露出它本来要盖住的那条边。

### 7.2 位置必须进渲染键，虽然它不改图片

渲染前的短路判断由两个东西驱动：图片**身份**变了就交叉淡入，完整参数集变了才做事。`position` 既不改变图片内容也不改变它的尺寸，两者都不会因它变真。

所以它必须被显式写进 `renderKey`。漏掉它的症状是**静默的**：点九宫格，什么都不发生，直到别的什么恰好也动了，位置才跟着刷新一次。这类"改动被短路吞掉"的 bug 在截图里完全看不出来，因此它是引擎测试单独立项断言的对象——测试直接检查 `slot-0` / `slot-1` 的 `background-position` 在只改位置之后确实变了。

### 7.3 导入是一次写，不是 N 次

一次导入多张图（多选或拖拽）时，面板**只写一次状态**：

- 第 1 张进 `single`——那是用户判断这次导入的凭据；
- 其余进播放列表，因为一批候选图交给轮播才有用；
- 超出上限的部分**明确报数**，不静默吞掉。

逐张安装写起来更直接，但五张照片会重绘六次、把持久化文件写六次来达到同一个终态。慢的那部分（解码）本来就是逐张的，装进去不是，所以装一次。

解码循环本身是**串行而非 `Promise.all`**：每个解码持有整张位图，五张 12MP 的照片同时解码就是几百兆活像素，笔记本上标签页会先死。而且**一个文件失败不中止整批**——五张里第三张是改错后缀的文本文件时，用户要的是另外四张，所以失败被收集起来和成功一起上报，而不是盖过它们。

## 八、刻意没有做的事

设计里同样重要的是边界。以下都是明确排除的：

| 没做 | 原因 |
| --- | --- |
| 改写输入框 / 对话框的材质 token | 那是皮肤系统的职责。壁纸插件碰它，就是把爆炸半径白白扩大 |
| 给内置壁纸打包图片 | 体积、版权、可派生性三项全输 |
| **在线图库（"装上就有图，不用自己导"）** | 门槛不在服务器，也不在数据库——**在图片托管与授权**。见下 |
| 引入框架或第三方运行时依赖 | 壁纸本身不需要框架；`react` 只用于挂载设置面板，取不到时壁纸照常工作 |
| 把插件状态和主题状态合并 | 主题是宿主的，壁纸是插件的。合并之后任何一方换代都会牵动另一方 |
| 用 `setInterval` 实现"每分钟检查一次" | 睡眠、时钟跳变、节流都会让它失准；纯函数 + 单个定时器能做对 |
| 自由拖拽式的 `background-position` 偏移 | 见 7.1。九种离散选择解决的是"主体别压在边栏下"，连续偏移会让这个控件需要自己的持久化、吸附与重置语义 |
| **把视频当壁纸**（循环、常驻、在内容后面） | 与"长时间使用不打扰"的目标直接冲突，且会持续占用 CPU。**注意这和开屏视频不是一回事**：开屏是一段一次性播放、拿到第一帧就让界面可用、播完即走的片子，它的存在时间以秒计，不是以小时计 |
| 让开屏在没有遮罩的页面上播放 | 遮罩和开屏是同一个决定；没有那块黑，片子落上去只会变成"界面闪一下然后被盖住"。这种情况下面板说的是"重新加载后才会看到"（见 `SPLASH-SPEC.md` §6.7） |
| 开屏用 OS 原生文件对话框拿绝对路径 | 浏览器拿不到绝对路径，但已有的导入管道能把 `File` 的字节交上来。跨平台零差异，砍掉三条平台分支，而且"传完选择设为壁纸或开屏"天然就是同一次导入 |

**关于在线图库。** 这一项值得写清，因为它看起来像个技术问题，其实不是：

- 它**不需要服务器**——壁纸 URL 就在插件自己的清单里，是一份静态列表，和现在手动粘贴 URL 走的是同一条渲染路径（`kind: "url"`，无域名白名单，只有协议与转义检查）。
- 它**不需要数据库**——没有用户产生的数据要存，列表是只读的。
- 它需要的是**一个稳定的图片托管，和这些图片的授权**。要"装上就有图"，图片必须由插件方持久托管（带宽与可用性由谁负责？）并且明确可再分发（谁授权？）。这两件事都不是代码能解决的，而且一旦内建，用户就失去了一件重要的事：**知道自己的壁纸上是什么、从哪来**。
- 因此这里的取舍不是"能不能做"，而是"该不该由这个插件承担"。选择不做，把自定义做扎实：多选导入、拖拽导入、导入时实测亮度、位置控制。
